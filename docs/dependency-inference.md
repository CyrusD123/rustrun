# Design: inferring dependencies without a header

Status: **proposed**. This is roadmap item 2: work out which crates a script
uses from its `use` statements, namespaced paths and macros, so the
`// deps:` header becomes optional.

## Summary

Don't try to guess crate names ahead of time. Build the script with no
inferred dependencies, read rustc's JSON errors for crates it couldn't find,
add those crates, and build again. This **compiler-feedback loop** usually
settles in 1–2 rounds. The compiler does real name resolution and macro
expansion, so it never mistakes a local module, a macro-generated item or a
glob import for a crate.

Some things the compiler can't tell us, so we still need a little logic of
our own: three small lookup tables (features, macros used without an import,
and import-name → package-name) and some safety checks before installing
anything automatically.

## Why not parse the source with `syn`?

The first option we considered was a static pass:

1. Walk the module tree (`mod foo;`, `#[path]`, `include!`).
2. Build each module's scope (local items, `use` names, generic parameters).
3. Collect the first segment of every path (`foo` in `foo::bar`).
4. Subtract std, the prelude, primitives and everything in scope.

Whatever is left counts as a crate.

The problem is which way its mistakes go:

- **Missing a crate is safe.** The build fails and the error names the crate.
- **Adding an unneeded crate is dangerous.** When a local module and a
  dependency share a name, the local name wins with no error. The build still
  succeeds, but we've downloaded an unneeded crate and run its build script.
  crates.io has a crate under almost every common word (`utils`, `config`,
  `gen`, …).

A static pass adds unneeded crates in exactly the cases it can't see:
- names created by macro expansion (a local `macro_rules!` that defines `mod gen {}`),
- glob imports (`use tokio::*;` then `time::sleep(..)`),
- names that only appear inside macro DSLs.

rustc sees all of these correctly.

## Evidence

Probes run against rustc 1.99.1. The identifier is taken from the error's
source span.

| Probe | What rustc reported | What it means |
|---|---|---|
| Several missing crates at once | E0432/E0433 for **every** missing crate in **one** compile, including `itoa` used inside `println!` | Round 1 finds every crate named directly |
| `serde_derive` present, `serde` missing | E0463 "can't find crate for `serde`" (span: the derive) | Code generated by derives can need a **second round** |
| `use semver::*;` with a later `time::Duration` | only `semver`; **no error for `time`** | rustc holds back errors that an unresolved glob might explain, so there's no false positive |
| Typo `colections::HashMap` | "missing a crate named `colections`" plus the note "consider importing this struct" | Typos look like missing crates and need filtering |
| `serde` without the `derive` feature | "cannot find derive macro `Serialize`", with no feature hint | Features need a table |
| `#[tokio::main]` without the `macros` feature | E0433 "cannot find `main` in `tokio`", with no feature hint | Same as above |
| `lazy_static! {}` with no import | "cannot find macro `lazy_static`", no crate hint, no error code | Macros used without an import need a table |
| An extra dependency the code never uses | `-W unused_crate_dependencies` reports "extern crate `itoa` is unused" | Wrong guesses can be removed after a successful build |

## How many rounds?

The number of rounds depends on how deeply crates are hidden, not on how
many crates there are:

- **Round 1** compiles no dependencies, so it's about as cheap as a
  type-check. It reports every crate that appears by name: in `use`
  statements, in paths, in attributes such as `#[tokio::main]`, and inside
  std macros.
- **Round 2+** is only needed when adding a crate reveals another one:
  - code generated by a derive needs a crate the source never names
    (`serde_derive` needs `serde`);
  - an unresolved macro's arguments aren't expanded until the macro's crate
    exists (`foo::m!(bar::x)`).

  In practice that's 1–2 rounds, rarely 3. Cap the loop at around 5.
- **Compiling the dependencies dominates the cost**, and that's paid either
  way. The extra rounds only add failed compiles of the script itself. Those
  stop at name resolution, before type checking, so they're fast.
- **Steady state is free.** Inferred crates go into the existing
  `resolved.json` cache. A later run only starts another round if its build
  fails with a missing crate.

## Algorithm

```text
deps := header deps ∪ cached inferred deps
tried := {}
for round in 1..=MAX_ROUNDS:
    result := cargo build --message-format=json
    if result is success: break
    candidates := missing-crate identifiers from errors (see below) − tried
    candidates += table lookups (features, macros used without an import)
    if candidates is empty: show rustc's errors as-is and exit
    tried ∪= candidates
    for each candidate: map to a package, run the safety checks, resolve its version
    deps ∪= accepted candidates
cargo rustc --bin <script> -- -W unused_crate_dependencies   # remove wrong guesses
```

### Reading the errors

- **Don't match on the message text.** It has changed across rustc versions:
  - older: "use of undeclared crate or module `foo`"
  - around 1.85: "use of unresolved module or unlinked crate `foo`"
  - 1.99: "cannot find module or crate `foo` in this scope"
- **Use the error codes** E0432 (unresolved import), E0433 (failed to
  resolve) and E0463 (can't find crate), and take the identifier from the
  primary span's highlighted text.
- **Only count errors from the script itself:** `reason ==
  "compiler-message"`, `target` is our bin, and the span is in one of the
  script's files. A dependency that fails to build must never be mined for
  crate names.
- **E0463's span points at the item that needed the crate** (for example
  the derive), not at the crate's name. Get the name from the message or
  from the derive's crate.

### Removing wrong guesses

Run `-W unused_crate_dependencies` only on the script crate, through
`cargo rustc --bin <name> -- …`. Putting it in `RUSTFLAGS` would rebuild
every dependency. Drop any inferred dependency it reports and save the result.
This only cleans up afterwards: the unneeded crate's build script has
already run.

## What the compiler can't tell us

1. **Typos.** `colections` looks exactly like a missing crate. Filters:
   - skip a candidate when rustc's notes include "consider importing" (that
     points to a missing `use`, not a missing crate);
   - skip names within one edit of a std module;
   - require a minimum number of downloads (see Safety).
2. **Features.** A table keyed on (crate, missing item), consulted after each
   failed round, for example:
   - (`serde`, derive `Serialize`/`Deserialize`) → feature `derive`
   - (`tokio`, `main`) → features `macros`, `rt-multi-thread`

   Possible general fallback: search the dependency's downloaded source in
   `~/.cargo/registry` for the `#[cfg(feature = "…")]` that hides the missing
   item.
3. **Macros used without an import.** `lazy_static!`, `json!`, `anyhow!`
   with no `use`. Needs a macro → crate table. Some entries are ambiguous
   (`info!` could be `log` or `tracing`); flag those rather than guess.
4. **Import name ≠ package name.** rustc names the identifier, not the
   package. The crates.io index doesn't record a crate's import name, so we
   need an override table (like pipreqs' mapping file), ranked by download
   count when ambiguous. Examples: `md5` (`md5` or `md-5`), `sha1` (`sha1`
   or `sha-1`), `argon2` (`argon2` or `rust-argon2`), `ini` (`rust-ini`).
   We already try `_`/`-` swaps (`proc_macro2` → `proc-macro2`).
5. **Renamed dependencies.** If the code uses `bar::` but the package is
   `foo`, and no `extern crate foo as bar;` says so, this can't be detected.
   Only a header override can fix it.
6. **API version mismatch.** LLM code written for `rand` 0.8
   (`thread_rng()`) fails against 0.9 even though the crate name is right.
   Stretch goal: when build errors are in code that uses crate X, retry X's
   previous major version.
7. **Code switched off by `#[cfg]`.** rustc only resolves code that's
   switched on for this platform, so `#[cfg(windows)] use winapi;` is never
   reported on macOS. That's correct for running the script here, but the
   script won't be portable without target-specific dependencies.

## Safety

Auto-installing crates named in LLM-written code invites **slopsquatting**:
attackers publish packages under names that LLMs tend to invent. Build
scripts and proc macros run arbitrary code at compile time. Before the first
build that uses any newly inferred crate:

- list the inferred crates (with versions) and ask for confirmation; `--yes`
  skips this for non-interactive use;
- warn about crates that are very new, have few downloads, or sit within one
  edit of a popular crate's name;
- never prompt again for crates already confirmed (they're in `resolved.json`).

## Interaction with the header

The `// deps:` header becomes an override rather than a requirement:

- `// deps: md-5` forces a package mapping.
- `// deps: serde[derive]` adds features and skips the feature table.
- `// deps: tokio@1` pins a version requirement.
- A new form such as `// deps: !utils` suppresses a wrong guess.

Inferred crates go through the existing `resolve()` pipeline, so version
selection, rust-version awareness and caching don't change.

## Plan

1. JSON-diagnostics loop: E0432/E0433 discovery, round cap, cache integration.
2. Second-round discovery through E0463 (code generated by derives).
3. Removing wrong guesses with `unused_crate_dependencies`.
4. Typo filtering, plus safety checks and the confirmation prompt.
5. Tables: features, macros used without an import, import-name → package.
6. Stretch: major-version fallback; target-specific dependencies.

## Testing

- **Fixture folder:** each script states its expected dependencies in a
  comment (`// expect: serde[derive], rand`), checked by a test harness.
  Cases: one round, the E0463 cascade, glob imports, typos, a local module
  sharing a crate's name, macro-generated modules, renamed crates, macros
  used without an import.
- **Offline:** tests use a fake sparse index, as `tests/cli.rs` already does.
  Fake crates must be real `.crate` sources too, served from a local registry
  (`[source]` replacement), so the loop can actually compile against them.
- **Evaluation:** a set of real LLM-generated scripts, measuring how many
  inferred crates are correct, how many real ones are found, and how many
  rounds it takes. This covers the project's "run any Rust file without
  modifications" success metric.
